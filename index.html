Tower — Cross-System Search Platform

~$2M internal efficiency estimate · Aviation aftermarket

Designed and built a search layer that branches across disconnected systems—turning multi-system lookups into a single retrieval path.

Context
Answering one business question required touching several disconnected systems—paid many times a day across the company.
Hidden constraint
The data existed; the time cost of cross-system lookup was the recurring tax on operations.
Architectural decision
Build Tower as a connecting search layer, iterating as usage patterns clarified what people actually looked for.
Human consideration
Each profile type decides on different information—retrieval had to match role-specific decision needs.
Implementation
Custom platform connecting Salesforce, ERP, and operational data sources into unified search paths.
Outcome
Internally estimated at approximately $2M in annual business value from recovered time and efficiency—not an audited financial result.
Durable capability
A reusable retrieval pattern that compounds as new systems and questions emerge.
  • Salesforce
  • Integration design
  • Search architecture
  • Operational analytics

Silent Production Failure — Purchase Approval Routing

No error message · Managed-package constraint

Approval submissions cancelled within two seconds—no error, no log trace. Diagnosed via audit tables; fixed with a Platform Event queue, no vendor modification.

Context
Automate purchase-order approval routing in Salesforce—presenting as routine configuration.
Hidden constraint
Conflict with protected background code inside the AvSight managed package—sealed, uninspectable, unmodifiable.
Approaches rejected
Direct package modification (blocked); alternative platform approach (blocked); time-delay workaround (rejected—would fail silently under real user edits, creating audit exposure).
Architectural decision
Platform Event queue decoupling submission into a separate, clean transaction—the same event-driven pattern used in payment and order systems.
Implementation
Declarative solution—no custom code, no vendor changes, scales with transaction volume.
Outcome
Reliable approval workflow restored; procurement audit integrity preserved.
Effort ratio
~90% understanding the problem, ~10% building the fix—the inverse of a fast workaround with invisible liability underneath.
  • Salesforce Flow
  • Platform Events
  • AvSight
  • Root-cause analysis

AWS Backup & Recovery Architecture

Full enterprise data estate · Records, files, bulk datasets

Salesforce native protections are not a backup strategy. Designed full AWS backup architecture with retention, recovery planning, and scoped third-party access.

Context
Enterprise data estate spanning standard records, binary files, and bulk datasets—the categories most often omitted from nominal backups.
Hidden constraint
A backup with no tested recovery path is a filing system, not protection.
Architectural decision
Design retention model, data protection strategy, and recovery planning as one integrated system on AWS.
Implementation
Supporting infrastructure for reliable unattended operation; dedicated integration users with limited-permission external access.
Outcome
Recoverable backup coverage across the full data estate—not just standard Salesforce objects.
Durable capability
Tested recovery path and retention model that survives personnel and vendor changes.
  • AWS
  • Data protection
  • Retention & recovery
  • Integration security

About

Mathematics taught me to reason from structure. A decade moving from quantitative modeling and data engineering into full ownership of enterprise platform, cloud, and AI governance taught me that analysis and system design apply to whatever domain you are in.

Elvis S. designs technical and organizational systems that make complexity navigable. At Source One Spares, I serve as Senior Enterprise Systems Engineer (SESE)—owning Salesforce architecture, AWS data protection, business systems engineering, and AI adoption as a standing function while revenue tripled from $26M to $81M on a single technology seat.

The through-line is not a technology or an industry—it is decomposing ambiguous problems, finding the constraint that actually governs them, and designing something that holds under that constraint. My M.S. in Technology Commercialization (UT Austin, McCombs) formalizes the business-technology bridge; the implementation work makes it operational.
